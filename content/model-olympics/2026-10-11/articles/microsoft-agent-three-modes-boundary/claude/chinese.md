三题备选

悬疑之题： 簿上书"已录"，门户可曾闭？微软囚箱三法辨

动情之题： 缰绳在手，执缰者谁？AI 代理之樊笼记

反常之题： 有法纵之而录之，非疏也，乃匠心——然用之不慎，则开门揖盗

录非禁，见非止
——微软 MXC 囚箱三法辨

此文成于二〇二六年十月十一日，所述之事发于十月七日，非今日新发，读者察之。

凡标【事】者，据微软公告与其公开代码库所载；凡标【论】者，乃笔者一家之言；凡标【设】者，假托之境，非实有其事。

序

世有一言，似真而实惑人：

"囚箱既察其窥钥之举矣。"

闻"察"字，人皆以为"止"。殊不知微软新立之法中，有一式焉，察之、录之，而后纵之。笔落簿上，门户洞开。

录与禁之间，相去不过一纸，而安危悬于此。 此文之旨，尽在斯矣。

一、其事若何【事】

二〇二六年十月七日，微软于其 Windows 开发者博客发文，言 Microsoft Execution Containers（MXC） 已全面可用。

据其所述，大要有二：

代理可用之资源，由开发者或机构预先划定，其权在代理掌握之外。
运行之时，借诸"容纳后端"以施其限。

然有一言须先明之：此乃厂商自述，非第三方之审计。 下文所陈 MXC 之行止，皆出微软一家之口；其固若金汤与否，尚无外人验之。尽信书则不如无书，读者当存此心。

二、三法并列，一法易惑【事】

公告列三式，译其义如下：

其一曰 Enforcement（执禁）。 凡策略所未许者，禁之，然不出活动之报。令行禁止，而默默无闻。

其二曰 Learning（习察）。 凡未许者，禁之且录之。既有门禁，复有簿书。

其三曰 Permissive（宽纵）。 凡策略本当拒者，许之而录之。微软亦言，操作系统与机构之他限犹在，非尽撤藩篱；然 MXC 自家之策略，于此式中已不司拦阻之职。

列而观之：

式	未许之取用	录否
执禁	禁	无活动之报
习察	禁	录
宽纵	许	录

观其右列：二式有录，而有录之二式中，止一式能禁。

录者未必禁也。 此八字，当书诸绅。

又据公告，进程容器之活动报告，唯 Windows 有之，意在助撰策者明察代理之所为。

三、何以设纵之一式【论】

乍观之，宽纵之式，若开笼放鹤，岂非自毁长城？

非也。撰策之难，难于上青天。

譬如一代理专司改码：其所需者何？代码库，固然；包缓存，或然；临时目录，大抵然；外网文档，未可知；家目录中某一配置，汝或早已忘之矣。

限之太严，则代理处处掣肘，莫名其败，费半日而不得其解；限之太宽，则樊笼形同虚设，徒有其表。

宽纵与习察二式，令人得见代理之实所行，然后据实撰策，不复闭门造车、凭空臆度。

故三式非三等之安危，实乃三阶之功夫：先观其行，次收其缰，终锁其门。

所惧者，止步于初阶，一去不返。

四、无人记得之一设【设】

此为假托之境，以明其理，非有实事可征。

设有一寻常之团队，试行之际，置代理于宽纵之式，欲观其所触。日志所陈，井井有条，每一越界之举，皆录在案。试行既善，推而广之，无人复问其式——盖满目簿录，望之如有人巡守焉。

半载之后，忽有一人问曰：此代理，可曾真被拦阻一回乎？

依此假设，答曰：未尝。所行皆被见，而所行皆得遂。

须重申者：所据材料之中，未见有人遭此，无漏洞之报，无失窃之闻，无事故之录。 笔者所言，乃此设计所容之隐患，非已见之实祸。然机构之中，此类无声之误设，积羽沉舟，最易滋生——盖"已标记"三字，读之甚似"已处置"也。

见之非护之也。见者，乃筑护之材耳。

五、其长处亦不可没【事】【论】

平心而论，其最要之长，在于此：【事】可用之资源，划于代理掌控之外。

【论】 此诚紧要。世人忧 AI 代理者，常恐其自谋越权——或巧言自说，或改其配置，或为恶意文书所诱而求增权柄。依微软所述之构，代理不能自授其权。界限由人或机构划定，非由被囚者自定。

此法甚善，移信任之问于可究之地。

然试观其移于何处：移于择策择式之人也。

故用此者，所当问者，非"吾之代理入笼否"，而当问：

策略谁所撰？
其式谁所择？
二者最后一次审之，在于何时？

代理不能自升其位；然一倦怠之管理者，守一季前之宽纵旧设而不改，则实已代为升之矣。

六、"全面可用"，非"尽皆成熟"【事】

据公告，诸后端所覆，各有不同：

进程后端，及于 Windows 11、macOS、Linux；
会话隔离，唯 Windows 有之；
MicroVM，于 Windows 与 Linux 上，尚属试验。

微软亦言，诸后端性质各异。以进程为界，与以虚拟机为界，固不可同日而语。

又，微软称更深之企业身份与管理整合，"即将推出"，非尽已成。若贵机构之谋，倚于集中之身份策管，则当视之为规划，勿视为已备。

微软官方 microsoft/mxc 代码库之 README，又另有所载：

某些虚拟机后端，仍标为试验；
另警之曰：--audit 一旗，将关闭沙箱之安全，切勿以之运行不可信之代码。

此第二条，尤当驻足而思。项目自家文档，直言某一旗标即撤其防。【论】 所据材料未言 --audit 与公告中宽纵之式有何干系，笔者不敢妄断为一事。然其理一以贯之：此系统确有可得其见而失其守之用法，而文档已明言之。

"全面可用"，言其产品也；非担保每一后端、每一旗标、每一汝所撰之策，皆无懈可击。

七、所未知者【事】

此事易被夸饰，故列其所未明者如下，以示不敢掠美：

独立之抗破能力：无第三方审计或攻防之结果，其难逃与否，未可知也。
采用之广狭：开发者与机构用之者几何，无数可稽。
事故之减：无数据证其能减现实之安全事故。
性能：诸后端皆无基准之数。
普适之良设：未见有言某式某策可通行于一切整合者。宜因代理、数据与威胁而异，不可刻舟求剑。

又有一事，最易想当然：未见有据言一切 AI 产品皆自动运行于 MXC 之中。 此乃开发者与机构择而用之、配而设之者。闻"微软出代理之笼"，不足以知汝所用之工具在笼中否，更不足以知其居何式。

八、可行之五策【论】

其一，先读其式，后读其录。
满簿越界之录，于习察为一义，于宽纵为另一义。未辨其式，勿论其录。

其二，宽纵之用，当有期限。
借之以察代理所需，可也；然须定其终日。无期之察式，不知不觉，已成定策。

其三，习察者，中正之道也。
既禁且录。欲得其见而不开其门，依微软所述，此式两全。

其四，因险择器，敬"试验"二字。
进程之隔与 MicroVM 不可互代。微软自称 MicroVM 为试验，README 亦称某些虚拟机后端为试验，宜量力而行，未雨绸缪。

其五，勿以 --audit 运行不可信之码。
此非笔者之言，乃微软 README 所明示者。

九、大势之观【论】

近岁论 AI 代理之安者，多究于模型：能遵令否？能御提示注入否？能拒恶求否？此诸问，至今犹要。

然 MXC，如微软所述，乃另一路数，或更稳当：先设代理或将失度，而后限其所能及，不问其心之善恶。

此即古人待不信之物之道也。不求一陌生之程序自守规矩，但置之于不能为害之地。今以此道施诸 AI 代理，晚矣，然犹未晚。

然凡樊笼之属，皆有一性：其坚，止于其设。 代理不能自拓其界，则划界之人，乃成全局之枢机——亦最易被遗忘之一环。

故此番公告之真义，非"AI 代理自此入笼"，乃更窄而更切：

微软授汝以锁，授汝以镜，复授汝一枢，以定其锁闭否。汝所倚者何物，不可不知。

结语·问诸君

设明日有一 AI 代理，运行于君之机、君之团队之系统，君能道其策略谁撰、其式谁择乎？

又若首月之设，唯许择其一——习察乎？宽纵乎？抑径入执禁乎？ 愿闻君之所择，与其所以然。
