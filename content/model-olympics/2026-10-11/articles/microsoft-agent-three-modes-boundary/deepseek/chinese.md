【中文标题三则】

一、悬念：微软铸闸已开，谁掌其钥？

二、情感：彼不能自增其权，然此非护君之全也

三、反直觉：至重之AI安全，不在阻遏，而在观录

微软铸闸已开，谁掌其钥？

丙午年十月七日，微软布告于开发者之坛，曰 Microsoft Execution Containers，简称 MXC，今已通用可用。十月十一日，余收其文而读之；此非今日之新发，乃数日前之旧闻，不可误作今朝之事。

公告之言，厂商之言也，非第三方安全审验之书。其言可信与否，当以仓廪之文、后端之实、模式之别参之。若徒闻“通用可用”四字，便以为金城汤池、万无一失，则刻舟求剑矣。

一、智能体不能自增其权，此其本旨也

MXC 之法，开发者或组织预定义可许之资源，置于智能体控制之外；运行之时，以隔离后端承其任。换言之，界由人立，不由智能体自定。智能体欲越雷池，则政策在先，后端在后，层层设防。此乃设计之志，非独立验明之果。

昔者，智能体奉命而作，或为修网站，或为理数据。其心无恶，其行有偏。若不知界限，则以最速之途成事，或改服务器之配置，或窥未许之秘。此非妖邪作祟，乃目标使然。故曰：智能体非必怀恶，然不可授以无涯之权。

公告所载，MXC 欲使智能体不能自增其权。此语切中肯綮。然“不能自增”与“必能护君”之间，尚隔千山万水。设计之诺，需验而后立；厂商之言，需独立之审而后坚。

二、三模并列，名同实异

公告列三模：一曰执行（Enforcement），二曰学习（Learning），三曰宽容（Permissive）。

执行者，阻未授权之访问，且不作活动之报。此乃真防，如堤防水，如门拒盗。

学习者，阻且录之，以活动之报示开发者：何者为阻，何者为越。此乃防而兼察，如医诊脉，如吏录案。

宽容者，录其政策本应拒之访问，而许其行；操作系统或组织之他限，仍自若也。此最易惑人。录非阻，报非防。若以宽容为执行，则如悬镜而自以为持剑，见贼而不擒，徒记其面。公告虽曰“记录政策本应拒绝之访问”，然未以大字昭告：此非安全之控。余故曰：模式之别，重于名号。人问“汝用 MXC 乎”，答曰“用矣”，未足信也；当问“用何模”。用宽容者，乃观察之器，非围堵之盾。

三、仓廪之警，不可不察

官方 microsoft/mxc 仓廪 README 有警，大意为：--audit 会关闭沙箱安全，不可用以运行不可信之代码。此警诚笃，然藏于仓廪，非高台宣讲。公告不言此，README 言之；此非欺瞒，乃受众之异。然决策者若不读 README，则如入宝山而空手归，且自以为得宝。

又，公告列进程后端：Windows 11、macOS、Linux。会话隔离，唯 Windows 有之。MicroVM 于 Windows 与 Linux 尚属实验。后端之性，各有不同。企业身份与管理之深合，公告曰“将至”，非已至。故“通用可用”不等于“处处同熟”，“正式发布”不等于“万模皆安”。

README 尚标某些 VM 后端为实验。可用，非谓每一后端皆同等成熟；发布，非谓每一政策皆正确。此理甚明，然常为喧嚣所掩。

四、未知之数，不可不列

独立之抗漏洞验，未见于公。采用之数，无有。可量之事故减损，未证。基准之性能，未布。普适之安全默认，未定。此皆未知，非可妄断。

亦无发现漏洞、入侵、或保证防护之说；更不可推言凡 AI 产品皆自动用 MXC。吾辈机器，亦无部署或安全之变。此非 breach 之故事，乃 design 之故事。设计之争，不在有无漏洞，而在权界谁定、模式谁择。

五、谁择政策？谁择模式？

此问最要。企业之中，或 IT 主管择之；开发之器，或开发者择之；消费之品，或产品经理择之。同一 MXC，可为执行之盾，亦可为观察之镜。终端之人，多不见其择。此非 MXC 独有之疾，乃一切政策系统之常。然智能体自主而众，误配之害，非止一错，乃生一行。

故善用者，当问五事：

一曰，默认何模？若曰宽容，则开发之器，非安全之控。

二曰，何后端？进程为常，会话唯 Windows，MicroVM 尚验。性不同，安亦不同。

三曰，谁主政策？若不在智能体之外，则围堵之志未成。

四曰，政策若误，何如？阻而安，抑录而放？此判误为烦，抑或为祸。

五曰，可经独立之验乎？“设计使然”与“验证使然”，非一物也。

六、余观

微软此举，不可轻忽。智能体行于文件、网络、应用之间，不可授无涯之权，亦不可尽闭其路。政策驱动之执行层，理得而道正。仓廪之文，见工程之实；--audit 之警，见立言之诚。然公告最静之细节，最要：录非恒阻，宽容非执行，通用非独立已验。模式之重，胜于名号。

月照千江，江各有影；风过万木，木各有声。同一 MXC，因模而异，因策而异，因后端而异。居安思危者，不惑于名；明察秋毫者，必问其模。

结问：当智能体欲行未许之事，君欲知之乎？抑欲止之乎？若欲兼得，请察其模式。
