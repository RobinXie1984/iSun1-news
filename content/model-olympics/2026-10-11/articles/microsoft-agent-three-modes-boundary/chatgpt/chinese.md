标题二｜共鸣：愿借机心分尘劳，谁替人间守寸疆
标题三｜反直觉：不能自封，亦可过界——微软智能体边界辨

城垣既筑，关钥谁执

夫记其越界，未必止其越界；见其留痕，未必知其受阻。

此微软新告之要义也。

公元二〇二六年十月七日，微软发布开发者公告，称其 Microsoft Execution Containers，简称 MXC，已正式可用。其法以开发者或组织预定智能体可用之资源，置权限之裁定于智能体掌控之外，再由运行时借不同隔离后端施行约束。

若以城郭喻之，则行事者受命入城，而不得自行刻印授爵、增拓疆土。许其往何处，取何物，用何器，皆须另有定规。

此制之意，可谓权有所出，行有所限。

然城垣既筑，是否凡逾界者皆止于关前？

未必。

据微软公告，运行之式有三：或拒之，或拒而记之，或许其行而记之。模式一殊，结果遂异。

故此事最堪玩味者，不独在城墙之高下，更在关门之启闭；不独在智能体能否自取权柄，更在何人预先执掌关钥。

机不可自封，不等于门必不启。

设有一事，以明其理。此为假设，非实录也。

主人付智能体以一项工作，许其取用某项目目录中之材料。智能体行至中途，转而请求目录之外的资源。

此时，事由尚未可断：或任务确有依赖，或规则有所疏漏，或其行路迂回，取用非必需之物。单凭一次请求，既不可遽断恶意，亦不可径称合理。

然而系统不能待议论终结，方决定眼前之门开抑或闭。

于是，言语之托付，至此化为执行之裁决。

嘱其慎行，乃意旨；使其不得妄行，乃机制。意旨可写于纸上，机制须见于动作发生之际。两者相辅，而不可相代。

微软所述 MXC，正欲将资源权限之界，置于智能体自身控制之外。此中值得重视者，是行事者与授权者有所区分：不能因完成任务有所不便，便自行为自己添一枚通行之符。

然有此区分，尚不足以断言万无一失。

所授之权，或本来过宽；所用后端，性质未必相同；所选模式，亦可能允许政策原拟拒绝之访问。

界限之实，在其如何运行；边界之名，不能代其守御。

公告列三式，其义须辨，不宜望文生义。

一曰强制模式，Enforcement：未获授权之访问，予以阻断，而不提供活动报告。

二曰学习模式，Learning：未获授权之访问，予以阻断，并加记录。

三曰宽容模式，Permissive：凡依该政策本应拒绝之访问，予以允许，并加记录；惟操作系统及组织另设之限制，仍可能施行。

三者之别，至为明白。

强制者，止之而无此类活动报告；学习者，止之且记之；宽容者，就该政策而言，许之且记之。

尤其“学习”二字，易令人误以为暂且放行、徐观其变。然依公告所述，此式仍阻断未授权访问。反之，宽容模式虽有记录，却不能据此认定该访问已被阻断。

于是，同见一条记录，背后或是关门之前的止步，或是放行之后的留痕。

若不知模式，便不能仅凭记录，判断其究竟有无通过。

反过来，强制模式不提供活动报告，亦不可由此断言其未曾阻断。无此报告，与无此约束，原非一事。

灯可照见行迹，灯不因此成为门闩。

微软另述，Windows 的进程容器活动报告，可助政策制定者察看行为、修订规则。此项报告有其平台范围，不可不察；不能见一处可记，便谓诸平台皆同；更不能见一事已记，便谓一事已止。

然既立规则，何以复设宽容之式？

此问自有其理。

依笔者之见，一种可能用途，在于拟定政策之时，先察工作实际请求何种资源，再审视规则是否切合任务。此乃对用途的推论，不是对任何具体部署安全性的担保。

规则过窄，正当工作或寸步难行；权限过广，不必取用之物亦可能门户洞开。制定者需辨其间轻重，而活动记录可供参酌。

但记录只能提供线索，不能自行颁发正当性。

某资源曾被请求，不等于它理应开放；某次访问有助任务，不等于今后应一概授予。何者必需，何者偶然，何者越出本意，仍待人审。

所以，真正难处，未必尽在模型。

谁读报告？谁订规则？谁选模式？谁核对实际运行之配置？

此数问，看似案牍细务，实为权柄所系。若无人问津，则纵有条分缕析之记录，亦不过纸上风声。

智能体不能自增权限，而操作者选择一种较宽的运行方式，两事可以同时成立。前者约束行事者，后者体现授权者之选择。

其中无须有漏洞，亦无须有叛逆。

门依设定而开，正可能是系统如实执行之结果。

官方 microsoft/mxc 代码仓库之 README，尚有一项警示，不应淹没于发布消息之中：--audit 会关闭沙箱安全防护，不得以之运行不可信代码。

此为官方文档对特定选项的告诫，须按其本义理解。

“审计”之名，听来似有明察秋毫、纤悉无遗之意；然而名称给人的安心，不能替代行为本身的核实。它究竟保留何种防护，关闭何种约束，应据文档而论，不可凭字面想象。

且此项 --audit 警示，须与公告所列 Permissive 模式分别看待。所给材料不足以证明二者处处同义，不能笼统混称，仿佛皆为同一种“只看不拦”的开关。

可确定者，是这项警示确已写明；不可擅推者，是所有相关术语皆可互换。

事后有册，不能使事前未闭之门追溯而闭。踪迹可存，已经放行的访问却不会因留痕而化为未遂。

然此亦非发现漏洞之报道，非泄露事故之实录，更不足据以判定整个框架已然失守。

夸其坚不可摧，失之无据；见文档警示便惊呼城陷，亦失之无据。

论技术之得失，当使事实有其边界，正如权限应有其边界。

再看“正式可用”四字，亦须细辨。

微软公告称，进程后端覆盖 Windows 11、macOS 与 Linux；会话隔离仅限 Windows；MicroVM 在 Windows 与 Linux 上仍属实验性。官方仓库 README 亦将某些虚拟机后端标为实验性。

故框架正式可用，与其中所有部件同等成熟，不能画为一线。

如一港开埠，未必各船皆历尽风浪；如诸路通行，未必桥梁载重、关隘规制全然一致。此仅为比喻，意在说明：平台覆盖，不等于性质无别；可供采用，不等于验证已毕。

欲评一项具体部署，仅答“已用 MXC”，尚未足够。

须问其平台为何，后端为何，政策如何，模式为何。

现有材料不足以独立评定各配置抵御利用的强弱，亦不足为诸后端排定安全名次。所能确认者，是其性质与成熟度有所不同；既有不同，便不可一言蔽之。

公告又称，更深入的企业身份与管理集成即将到来。既谓将至，便不可写作已至。

远帆初见，未可记为归港；蓝图在案，未可尽算竣工。

此篇所据，乃微软开发者公告及其官方仓库说明，并非独立安全审计。依所给材料，尚无足以回答下列问题之证据：独立检验下能抵御何种利用，已有多少采用者，事故减少几何，性能基准如何，又是否存在适合所有集成的通用安全默认值。

未有此证，不等于已证其弱；但亦不可凭空补作其强。

不能因正式发布，便断言事故已减；不能因提供隔离机制，便许以绝对防护；不能因微软推出此框架，便称其所有人工智能产品皆已采用，更遑论天下诸家。

有一分证据，立一分判断。余者，留待验证。

于笔者观之，此事最值得深思者，乃问题的重心有所移动。

人常问：智能体聪明否，听令否，能成事否？

如今还须问：授它多少权，凭何规则授之，越界之时作何处置？

聪明是行舟之力，权限是可航之域。舟行千里固然可喜，然去往何处，不能全凭舟速作答。

若政策本已授予过多资源，智能体不必绕过边界，便可能取得超出任务所需之物；若模式本就允许政策原拟拒绝的访问，系统亦不必发生故障，访问便可继续；若报告忠实记录了一次放行，使用者却误以为那是一回拦截，则误解发生在人心，而未必发生在程序。

故最有用的一问，宜直抵关前：

当智能体请求未获授权之资源时，究竟会发生何事？

是阻断而无活动报告，是阻断并记录，还是允许并记录、另受其他限制？

能答清此问，方能使“边界”二字落到实处。

愿机心代人披星戴月，分担繁务，使人得还光阴于山川、亲友与未竟之志。然托付愈深，权限愈须明白；能行愈远，出入愈须有据。

微软此番所示，是一套由人定义资源边界、借后端施行约束的框架。其意义可议，其成效待验，其模式之差，则已值得读者看清。

城可筑，令可立，行迹亦可一一载录。

但史官有笔，不等于守将闭门。

那一道关，究竟止人，还是记人而放行，终须看谁执钥，又下了何令。

资料所据：微软二〇二六年十月七日开发者公告；
