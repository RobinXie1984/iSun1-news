# Windows 开始改写 NTLM 连接规则，下一道门槛会拦住谁？

微软正为 Windows 电脑与应用程序沿用的一套身份认证机制——NTLM——调整规则。自 2026 年 11 月 10 日起发布的相关更新，让完成更新的客户端在适用连接中默认提出使用密码学消息签名。它的作用，是帮助接收方检查身份认证之后传来的消息是否保持完整。第一阶段仍保留兼容空间：按照文档所述的默认设置，服务器同时接受带签名与无签名的客户端连接。

这项变化牵动的是许多机构日常运转中的旧依赖。安全技术逐年演进，仍有用处的应用则继续服役。一条连接可以安静运行多年，背后沿用什么规则，往往只有维护人员追查问题时才会细看。默认行为一经调整，这些依赖便逐渐显形；等到新规则成为接入条件，应用能否继续工作，就要看连接本身是否符合要求。

微软把第二阶段安排在 **2027 年 5 月**。届时，Windows 服务器将默认要求 NTLM 签名，缺少签名支持声明的客户端会遭到拒绝。公开时间表明确到月份，具体日期仍待公布。从今年 11 月的“提出使用”，走到明年 5 月计划中的“要求使用”，中间留下了一个实际问题：哪些连接已经采用这层保护，哪些连接到了门槛收紧时仍能通行？

要理解这件事，可以先从两台电脑之间的一次交谈说起。客户端提出请求，服务器提供资源。这两个名称指的是当次交互中的角色：一个应用向另一台电脑索取资料时，就在充当客户端，两端也可能同属一家机构。使用者眼前只是熟悉的界面、一次成功的操作；在其背后，双方还须商定这段交谈依照什么规则进行。

NTLM 是建立这种关系的一种方式。它帮助双方完成身份认证，并建立“安全上下文”，也就是此次交互共同采用的身份与保护条件。微软的技术资料将 Kerberos 列为适用场合下的首选认证协议。此次调整所关者，是仍在使用的 NTLM 连接；它在一家机构中影响多深，取决于具体应用究竟依靠哪些连接。

不妨用一个生活中的比喻来分清三件事：工作证、信件封签和遮住内容的信封。工作证帮助确认来者身份；封签让收件人察觉信件是否遭到改动；信封则把内容遮起来。这只是帮助理解的示意，分别对应身份认证、完整性保护与保密性保护。

核验了工作证，接下来仍须查看信件的封签。信件即使带着封签，内容也可能摊在旁人眼前。现实中的封签有其局限，数字世界的签名同样依赖具体的安全条件。理解这些分工，才能看清“登录成功”究竟回答了哪一部分问题。

微软的 NTLM 规范把签名与“密封”区分开来。签名负责消息完整性，帮助接收方检查受保护的消息在传输中是否发生改动；密封通过加密保护内容的保密性。“会话”指双方这一段交互，会话密钥则是完成相关密码学检查所用的信息，其用途与用户的明文密码有别。

因此，一次成功登录说明认证环节完成了相应工作，后续消息采用何种保护，还要看连接协商的结果。应用看起来照常运行，底层保护却可能因条件而异。这也是此次更新值得关注之处：它把人们通常视为一体的“连上了”和“消息受到保护”，展开成了可以分别检查的环节。

“签名”这个词本身还带着历史留下的歧义。微软区分了真正的密码学签名，以及名为 `ALWAYS_SIGN` 的旧式占位机制。后者单独存在时，密码学完整性保护处于缺失状态。当前受支持的 Windows Server 版本本就具备签名能力；此次变化集中在如何提出保护、如何协商、如何观察结果，以及何时将其列为必需条件。

一个名称可以沿用多年，其背后的实际行为却值得重新辨明。循其所动，真正有用的证据是双方商定了什么，以及那项约定究竟提供哪一层保护。对管理员而言，查清协商结果，才能把界面上的名称与连接中的实际保障对应起来。

微软称，这批更新处理了编号为 **CVE-2026-118737** 的漏洞。CVE 编号用于识别一项具体漏洞，便于不同厂商与研究者对应讨论。Windows 11 的 KB5132061 发布说明也确认了相关客户端变化，其适用范围限于该更新列出的 Windows 11 版本；其他操作系统的适用情况，应以各自的更新资料为准。

现有证据确立了这次由厂商宣布的安全调整。资料采集时，单独链接的微软安全响应中心漏洞页面访问受阻，因此漏洞严重程度、现实中的利用状态等信息仍待核实。当前材料足以解释机制与时间表；若要估算实际减少了多少攻击，还须取得部署后的测量结果。

微软说明的防护目标，主要涉及“中继攻击”。从高层次看，中间人把一段合法身份认证交互转送到另一个端点，借此谋求访问机会。其机会来自转接认证过程，掌握用户密码则是另一条问题线索。理解这类风险，需要沿着认证之后的交谈继续看下去。

消息签名可以在后续交互中设下一道关口。要生成有效的受保护消息，参与者需要掌握相应的会话安全信息。一个仅负责转送认证流量的中间人，到了需要提交有效完整性检查的下一步，便可能受到阻挡。接收方由此多了一种检查手段，用来核验接下来这段交谈的受保护消息。

这解释了签名的防护价值，也划出了它的作用范围。凭据窃取、密码破解、恶意软件和诱骗各有自己的机制；消息签名针对的是通信过程中的特定风险。它在某次交互中发挥多大作用，仍取决于密钥与协议条件。厂商资料描述了设计目的，真实组织中的效果则有待实测。

第一阶段为何保留无签名连接，答案在于兼容性。微软文档说明，当服务器对签名支持的回应缺失时，客户端可以退回旧有行为，让连接继续。匿名、空身份及来宾会话也列入豁免范围，这一安排延续到计划中的下一阶段。技术规范解释了这些会话缺少相应会话安全保护的边界；其具体访问权限，则由应用与运行环境决定。

这使过渡期呈现出两面相连的现实：连接能够继续，体现了兼容机制的作用；它究竟采用哪种保护，仍须查验。一旦服务器执行签名要求，能否满足条件便决定了接入结果。当前的回退路径服务于现阶段兼容，未来的强制要求则改变接收端的判断规则。

以一个仅作说明的例子来看，某业务应用只在定期编报时使用。它在一次工作日运行成功，为当次操作提供了证据。要判断它将来能否通过签名要求，还须知道它连接了哪个端点、采用何种认证方式，以及那次交互是否提出了签名支持。熟悉的应用界面，只呈现了整个过程的一部分。

微软关于兼容性的表述也有明确范围：受支持的 Windows Server 版本具备签名能力。一家机构实际使用的端点，却可能横跨其他软件、历史系统与各自行为不同的应用。从厂商支持说明走到对整家机构的判断，中间仍需补上实际连接的证据。

为此，微软提供了审计记录，用来提高连接行为的可见度。文档列出 NTLM Operational 日志中的客户端事件 **4022** 与服务器事件 **4023**；在启用相关增强审计的条件下，Windows Server 2019 及后续版本具有文档所述的增强事件信息。一个容易误读的细节是：带签名和无签名的示例，都可能显示为 *Warning*，即“警告”级别。

“警告”提醒管理员留意，具体判断仍要落到事件内容。双方提出了什么、最终协商了什么、形成了怎样的会话与密钥状态，这些细节才把抽象规则落到一次真实交互上。若把所有警告都归为无签名连接，结果就会发生误判。

观察范围同样影响结论。日志记载的是某些系统在某段时间内发生的活动。空白样本的解释范围，也受这些边界约束。例如，采样时处于离线状态的设备、月底才运行的应用，或偶发流程触发的连接，都可能落在观察范围之外。这些是说明覆盖问题的例子，表明审计持续多久、覆盖何处，会直接影响准备情况的判断。

因此，“已经准备好”应当对应一组明确的业务依赖。一次带签名的交互，为其当时的运行条件提供证据。把这个结果推广到其他设备、软件版本或未来操作，需要说明这些对象为何具有可比性。其道理与日常测量相通：看过哪些，在哪些条件下看过，决定了结论能够走多远。

发现无签名连接，也应按证据本身理解。它反映的是安全状态，以及值得追查的兼容问题。认定遭到入侵，则需要恶意活动证据。把两种判断各归其位，应用负责人便能准确追查依赖，安全人员也能评估连接实际获得的保护。

这场过渡会在不同人面前显现出不同样貌。普通用户关心熟悉的应用是否仍能打开、工作是否能继续；应用负责人知道哪些操作重要、何时才会发生；管理员则能查看系统状态与连接记录。当这些信息合到一起，一条技术事件才有了业务上的分量：它关联的可能是某项日常工作，也可能是一项周期较长、平时少见的必要流程。

微软允许管理员在审计后提前实施要求。这个选择把判断的重心放在本地证据上：相关依赖能否满足条件，拒绝一条连接会中断什么工作。发布日期提供时间坐标，机构自己的实际交互，才为中断风险的评估提供依据。

本文依据的公开材料，由资料采集者于 2026 年 11 月 11 日检查。微软支持公告与 Windows 11 发布说明同出一家厂商；技术背景与协议规范负责解释认证、签名和密封的含义。它们共同支撑了对机制与计划的说明。独立部署成效仍待验证，本次报道的取证范围限于文档，设备补丁操作、客户日志检查与运行测试均为零次。

由此，软件层面的进展与机构层面的进展，可以逐步辨清。更新改变客户端默认提出的能力，安装情况决定哪些设备获得这项行为，协商结果揭示某次连接用了什么保护，服务器的执行规则则决定哪些连接获准进入。每一层都有自己的证据，也各自回答一个问题。

按照微软目前公布的计划，2027 年 5 月，接收端的默认门槛将更严格。眼下这段时间，让那些多年安静运行的依赖有机会被看见。等到服务器要求出示签名时，维系日常工作的连接之中，哪些仍沿用无签名方式，缘由何在，又有哪些能够继续通行？
