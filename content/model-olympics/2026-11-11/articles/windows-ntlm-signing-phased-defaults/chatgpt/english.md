# Windows Is Changing the Rules for NTLM—Which Connections Will Survive the Next Step?

Microsoft is beginning a change to NTLM, a system that Windows computers and applications use to establish who is connecting. Updates released on or after November 10, 2026, make updated clients offer cryptographic message signing by default on relevant connections. Signing helps a receiving computer check the integrity of messages exchanged after authentication. For organizations running older applications alongside current Windows systems, that distinction matters: establishing identity and protecting the ensuing conversation are separate jobs. During this first phase, servers at the documented default continue accepting both signed and unsigned clients.

The change belongs to a larger problem familiar to anyone responsible for a long-lived computer system. Security capabilities evolve while useful applications remain in service. A connection may continue working for years, quietly depending on behavior that its owners rarely examine. Changing a default brings that dependency into view. Requiring the new behavior turns it into a condition of access.

Microsoft plans that second step for May 2027. Windows servers will then require NTLM signing by default, rejecting clients that fail to offer it. The published schedule specifies the month; the exact day remains unspecified. Between the November offer and the planned May requirement lies the central question: which connections actually use the protection, and which will still work when acceptance depends on it?

Understanding that question begins with the conversation between two computers. A client requests something; a server provides it. Those words describe roles in a particular exchange. An application asking another computer for a resource acts as a client, even when both machines belong to the same organization. The person using the application may see only a familiar screen and a successful operation. Underneath, the two sides agree on how the connection will proceed.

NTLM is one way they establish a security context: the shared basis for recognizing and protecting an exchange. Microsoft’s technical background describes NTLM as a Windows-supported authentication protocol and identifies Kerberos as the preferred protocol where applicable. This rollout concerns the NTLM connections that remain in use. Its scope is therefore a particular part of Windows authentication, with relevance determined by the applications and connections an organization actually relies upon.

An everyday illustration helps separate the jobs involved. Imagine a workplace identity badge, a tamper-evident seal on a message, and an opaque envelope. The badge helps establish who may enter. The seal gives the recipient a way to detect changes to the message. The envelope conceals its contents. These are three different protections, serving three different purposes.

In this illustration, authentication corresponds loosely to the badge, signing to the seal, and encryption to the envelope. A badge check establishes something about identity; the condition of the message requires its own examination. Equally, a sealed message may remain readable to someone who can see it. A physical seal has practical weaknesses, and the digital version also depends on the security of its underlying mechanism.

Microsoft’s NTLM specification distinguishes message integrity, provided through signing, from confidentiality, provided through a process called sealing. Signing uses cryptographic information associated with the session to help the receiver check a protected message. Sealing encrypts content. A session is the particular exchange between the participants, and its security key is information used to perform those checks. The key’s role is distinct from the user’s plaintext password.

For a reader watching an application work, these distinctions can seem remote. Yet the visible success of a sign-in answers only part of the security question. An application can establish access while the protection applied to subsequent messages follows a different set of negotiated conditions. That makes the details of the connection consequential even when the user experience remains familiar.

There is also a historical wrinkle in the word *signing*. Microsoft distinguishes actual cryptographic signing from a legacy placeholder called `ALWAYS_SIGN`, whose standalone integrity protection is absent. Supported Windows Server versions already possess signing capability. The November change concerns how protection is offered and negotiated, how administrators can see the result, and when servers will require it.

This makes labels a poor substitute for examining behavior. A setting or name may describe a convention whose meaning has accumulated over many years. The useful question is what the participants agreed to do and what protection that agreement supplies. In security work, the distance between a reassuring label and an effective check can be the distance between an apparent safeguard and a functioning one.

Microsoft connects the rollout to CVE-2026-118737, a vulnerability identifier, and says the updates address it. Its Windows 11 release note, KB5132061, corroborates the client change for the versions covered by that update. That identifier belongs to the specified Windows 11 release; applicability across other operating systems requires their corresponding update information.

The available documentation establishes an announced security change. The vulnerability’s severity and exploitation status remain unverified in the accessible material: the separate Microsoft Security Response Center record was inaccessible to the collector. The evidence supports explaining Microsoft’s mechanism and schedule. A numerical estimate of attacks prevented would require measured outcomes from deployments.

The stated security rationale concerns relay attacks. At a high level, an intermediary forwards a legitimate authentication exchange toward another endpoint. The attacker’s opportunity comes from carrying an exchange between participants. Knowledge of the user’s password is a separate issue, so a strong explanation of relay risk has to follow the conversation beyond the credential itself.

Signing can constrain what happens after that forwarded exchange. Producing valid protected messages requires the relevant session security information. An intermediary who merely carries authentication traffic may therefore reach a barrier when the next message needs a valid integrity check. That is the intended defensive value: the receiving system gains a way to check the protected continuation of the conversation.

The scope matters. Credential theft, password cracking, malicious software and deception each involve their own mechanisms. Message signing addresses a defined part of the communication problem. Its effectiveness in a particular exchange depends on the applicable keys and protocol conditions. The sources describe why the protection is useful; its effect across real organizations remains an empirical question.

Compatibility explains the shape of the first phase. Microsoft documents a client fallback to legacy behavior when a server fails to echo signing support, allowing the connection to continue. Anonymous and guest sessions remain exempt, including in the planned future phase. The technical specification describes their session-security limitations. Permissions for such sessions remain a separate question governed by the application and environment.

These boundaries give the transition its practical tension. A working connection during the first phase can show that compatibility behavior is doing its job. Its continued success also leaves a further question about the protection negotiated. Once a server enforces a requirement, a client’s ability to satisfy that requirement determines acceptance. Present-day fallback describes the current compatibility path; future enforcement changes the decision at the receiving end.

Consider an illustrative business application used only for a periodic reporting task. Its successful operation during an ordinary workday offers useful evidence about that particular run. A readiness judgment for a later requirement would also depend on which endpoint it reached, how it authenticated, and whether that exchange offered signing. The application’s familiar appearance tells its owner little about those details.

The same reasoning applies to the scope of Microsoft’s compatibility statement. Support for signing across supported Windows Server versions is valuable information. An organization’s actual collection of endpoints may span other software, older systems and applications with their own behavior. Moving from a vendor’s support statement to a conclusion about a whole organization therefore requires evidence about the organization’s connections.

Microsoft’s auditing provisions are intended to make those exchanges more visible. The documentation identifies client event 4022 and server event 4023 in the NTLM Operational log, a record of relevant activity. Enhanced events are documented for Windows Server 2019 and later under the relevant enhanced auditing. Both signed and unsigned examples can carry a *Warning* level, so the event details determine the interpretation.

A warning label is an attention signal. Treating every such entry as an unsigned connection would confuse the label with the underlying result. The informative details concern the negotiation and session state: what the participants offered, what they agreed upon, and what security context the exchange established. Those details connect the abstract policy to an actual transaction.

Coverage is equally important. A record describes activity observed by particular systems during a particular period. An empty sample establishes a limited observation whose meaning depends on those boundaries. A device that stayed offline, an application used at month-end, or a connection triggered by an unusual workflow may fall outside that observation. These are illustrative coverage problems, each showing why the duration and scope of an audit affect its conclusions.

Readiness is consequently a claim about a set of dependencies. To support it, an organization needs to connect observed behavior to the applications people rely on. A signed exchange provides evidence for that exchange under its observed conditions. Extending the finding to other devices, software versions or future operations requires a reason to regard them as comparable. This is ordinary measurement discipline applied to computer conversations.

The distinction also helps interpret an unsigned result. Such a finding identifies a security posture and a possible compatibility issue. Establishing compromise requires evidence of malicious activity. Keeping those judgments separate allows an application owner to investigate the dependency precisely, while security staff assess the protection that the connection actually received.

Different participants will encounter this transition at different levels. Ordinary users may experience its consequences through access to a familiar application. Application owners understand which operations matter and when those operations occur. Administrators can examine the systems and connection records. A meaningful readiness assessment draws those views together: technical observations gain business significance when someone can identify the work they represent.

Microsoft permits earlier enforcement after auditing. That option places weight on the quality of local evidence. The decision concerns whether the relevant dependencies can satisfy a requirement and what a rejected connection would interrupt. A release date alone supplies a schedule; the organization’s observed exchanges supply the basis for judging its own exposure to disruption.

The sources available for this article offer different kinds of support. Microsoft’s support notice and Windows 11 release note share the same vendor lineage. The technical background and protocol specification explain what authentication, signing and sealing mean. Together they provide a coherent account of the planned change. Independent deployment outcomes remain unestablished, and this reporting involved zero device patches, customer-log inspections or operational tests.

That leaves a useful distinction between progress in software and progress in an organization. The November update changes what updated clients offer. Installation determines where that behavior is available. Negotiation determines what happens in a particular connection. Enforcement determines which connections a server accepts. Each step has its own evidence, and each answers a different question.

By May 2027, under Microsoft’s published plan, the server’s default answer will become stricter. The interval gives organizations a chance to make previously quiet dependencies visible. The consequential question is now concrete: among the connections that keep everyday work moving, which remain unsigned, why do they remain so, and which will satisfy the requirement when the receiving server asks for proof?
